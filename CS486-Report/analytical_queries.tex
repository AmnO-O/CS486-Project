Phase~2 (project description \S1.3) introduces four reporting queries that
support the Facility Manager with accumulated booking and maintenance
history: (1)~total approved booking hours per space for a semester, (2)~the
number of approved bookings by weekday and hour for a semester, (3)~available
spaces satisfying a required capacity and facility list within a time period,
and (4)~approved bookings affected when a maintenance record is escalated to
out-of-service. This section describes their implementation in
\texttt{outputs/16-analytical-queries-G05.sql} and the results observed on the
generated dataset.

Each query is wrapped in a stored procedure (\texttt{dbo.usp\_task16\_q1}
\ldots\ \texttt{dbo.usp\_task16\_q5}) so that the same query body can be
executed repeatedly with different parameter sets, and each procedure validates
its inputs (for example, it rejects a slot with \texttt{@slot\_end <=
@slot\_start} with a descriptive \texttt{THROW}). The procedures share a small
set of conventions derived from the Task~09 schema:

\begin{itemize}[noitemsep]
    \item \emph{Confirmed bookings} are those with status
    \texttt{approved}, \texttt{checked\_in}, or \texttt{completed};
    \item soft-deleted rows (\texttt{is\_deleted = 1}) are always excluded;
    \item time intervals are compared with the half-open overlap predicate
    \texttt{@start < row\_end AND @end > row\_start};
    \item semester windows follow the U4 convention: Semester~1 is the
    half-open interval \texttt{[September 1, February 1)}, excluded summer.
\end{itemize}

All results in this section were obtained on 2026-08-08 by executing the
complete script against the Task~14 scratch database
\texttt{CS486\_G05\_T14} (120{,}000 bookings); the raw evidence is recorded in
\texttt{logs/eval/task16/}. The semester examples use Semester~1 of academic
year 2024--2025, \texttt{[2024-09-01, 2025-02-01)}.

\subsection{Approved Booking Hours per Space (Report~1)}

The first report answers: \emph{how many confirmed booking hours did each
space have in a semester?} All confirmed, non-deleted bookings whose requested
interval overlaps the semester window are included, and each duration is
clipped to the window so that a booking spilling over the semester boundary
contributes only its in-semester hours. The aggregation groups by the stable
space identity and orders by total hours descending so that the most loaded
spaces appear first:

\begin{lstlisting}[style=sqlreport]
WITH semester_bookings AS (
    SELECT
        booking_id,
        space_id,
        CASE
            WHEN requested_start_time < @semester_start
                THEN @semester_start
            ELSE requested_start_time
        END AS eff_start,
        CASE
            WHEN requested_end_time > @semester_end
                THEN @semester_end
            ELSE requested_end_time
        END AS eff_end
    FROM dbo.bookings
    WHERE is_deleted = 0
      AND status IN ('approved', 'checked_in', 'completed')
      AND requested_start_time < @semester_end
      AND requested_end_time > @semester_start
)
SELECT
    s.space_id,
    s.space_code,
    s.space_name,
    s.capacity,
    COUNT(sb.booking_id) AS confirmed_booking_count,
    ROUND(
        SUM(DATEDIFF_BIG(SECOND, sb.eff_start, sb.eff_end) / 3600.0),
        2
    ) AS total_hours_in_semester,
    ROUND(
        SUM(DATEDIFF_BIG(SECOND, sb.eff_start, sb.eff_end) / 3600.0)
            / NULLIF(COUNT(sb.booking_id), 0),
        2
    ) AS avg_hours_per_booking
FROM dbo.spaces s
LEFT JOIN semester_bookings sb
    ON sb.space_id = s.space_id
GROUP BY
    s.space_id,
    s.space_code,
    s.space_name,
    s.capacity
ORDER BY
    total_hours_in_semester DESC,
    s.space_code ASC;
\end{lstlisting}

\subsection{Bookings by Weekday and Hour (Report~2)}

This query characterises the demand pattern of a semester: \emph{on which
weekdays and hours do approved bookings start?} Knowing the weekday--hour
distribution of confirmed booking starts lets the Facility Manager align
staffing and opening hours with real demand. The weekday number must be
meaningful regardless of the session's \texttt{DATEFIRST}, so it is computed
with a pure integer expression anchored at \texttt{1900-01-01} and mapped with
a modulo-7 arithmetic to \texttt{1 = Monday} \ldots\ \texttt{7 = Sunday}:

\begin{lstlisting}[style=sqlreport]
WITH semester_bookings AS (
    SELECT
        booking_id,
        space_id,
        requested_start_time
    FROM dbo.bookings
    WHERE is_deleted = 0
      AND status IN ('approved', 'checked_in', 'completed')
      AND requested_start_time >= @semester_start
      AND requested_start_time < @semester_end
)
SELECT
    ((DATEDIFF(
        DAY,
        CONVERT(date, '19000101'),
        CONVERT(date, b.requested_start_time)
    ) % 7) + 7) % 7 + 1 AS weekday_number,
    CASE ((DATEDIFF(
        DAY,
        CONVERT(date, '19000101'),
        CONVERT(date, b.requested_start_time)
    ) % 7) + 7) % 7 + 1
        WHEN 1 THEN N'Monday'
        WHEN 2 THEN N'Tuesday'
        WHEN 3 THEN N'Wednesday'
        WHEN 4 THEN N'Thursday'
        WHEN 5 THEN N'Friday'
        WHEN 6 THEN N'Saturday'
        ELSE N'Sunday'
    END AS weekday_name,
    DATEPART(HOUR, b.requested_start_time) AS start_hour,
    COUNT(*) AS booking_count,
    COUNT(DISTINCT b.space_id) AS distinct_space_count
FROM dbo.bookings b
GROUP BY
    ((DATEDIFF(
        DAY,
        CONVERT(date, '19000101'),
        CONVERT(date, b.requested_start_time)
    ) % 7) + 7) % 7 + 1,
    DATEPART(HOUR, b.requested_start_time)
ORDER BY
    weekday_number,
    start_hour;
\end{lstlisting}

A half-open window is used: a booking contributes when its
\texttt{requested\_start\_time} lies in \texttt{[@semester\_start,
@semester\_end)}. With the same Semester~1 window the evaluation run produced
66 weekday/hour buckets, verified in the live evaluation; each bucket counts
the confirmed bookings that start in that hour and the number of distinct
spaces involved:

\subsection{Available Spaces with Required Facilities (Report~3)}

This report implements a room finder: \emph{which spaces satisfy a requested
capacity and every required facility during a given time period?} The caller
passes the slot, the minimum capacity, and the list of required facilities as
a JSON array, which the procedure normalises into a local table variable
before evaluating the availability criteria. Three conditions must hold
simultaneously for a space to appear in the result:

\begin{enumerate}[noitemsep]
    \item \emph{Capacity and facility fit} --- \texttt{capacity >=
    @minimum\_capacity} and the space has \emph{every} requested facility,
    verified by relational division (a double \texttt{NOT EXISTS}); a
    one-facility match is not sufficient;
    \item \emph{No booking conflict} --- no confirmed, non-deleted booking of
    that space overlaps the proposed slot;
    \item \emph{No hard maintenance conflict} --- no \texttt{open} or
    \texttt{in\_progress} maintenance with impact level
    \texttt{out-of-service} overlaps the slot; advisory maintenance does
    \emph{not} block availability.
\end{enumerate}

The core of the procedure is:

\begin{lstlisting}[style=sqlreport]
DECLARE @required_facilities TABLE (
    facility_name NVARCHAR(255) PRIMARY KEY
);

INSERT INTO @required_facilities (facility_name)
SELECT DISTINCT CAST([value] AS NVARCHAR(255))
FROM OPENJSON(@required_facilities_json)
WHERE [value] IS NOT NULL
  AND LTRIM(RTRIM(CAST([value] AS NVARCHAR(255)))) <> N'';

WITH booking_conflicts AS (
    SELECT DISTINCT b.space_id
    FROM dbo.bookings b
    WHERE b.is_deleted = 0
      AND b.status IN ('approved', 'checked_in', 'completed')
      AND @slot_start < b.requested_end_time
      AND @slot_end > b.requested_start_time
),
maintenance_conflicts AS (
    SELECT DISTINCT m.space_id
    FROM dbo.maintenance m
    WHERE m.is_deleted = 0
      AND m.status IN ('open', 'in_progress')
      AND m.impact_level = 'out-of-service'
      AND m.start_time < @slot_end
      AND (
          m.completion_time IS NULL
          OR m.completion_time > @slot_start
      )
),
facilities_ok AS (
    SELECT s2.space_id
    FROM dbo.spaces s2
    WHERE NOT EXISTS (
        SELECT 1
        FROM @required_facilities rf
        WHERE NOT EXISTS (
            SELECT 1
            FROM dbo.space_facilities sf
            INNER JOIN dbo.facilities f
                ON f.facility_id = sf.facility_id
            WHERE sf.space_id = s2.space_id
              AND f.name = rf.facility_name
        )
    )
)
SELECT
    s.space_id,
    s.space_code,
    s.space_name,
    s.space_type,
    s.capacity,
    s.current_status AS status_hint,
    STRING_AGG(f.name, ', ') AS facility_summary
FROM dbo.spaces s
LEFT JOIN dbo.space_facilities sf
    ON sf.space_id = s.space_id
LEFT JOIN dbo.facilities f
    ON f.facility_id = sf.facility_id
LEFT JOIN booking_conflicts bc
    ON bc.space_id = s.space_id
LEFT JOIN maintenance_conflicts mc
    ON mc.space_id = s.space_id
WHERE s.capacity >= @minimum_capacity
  AND s.current_status NOT IN ('retired', 'temporarily_closed')
  AND bc.space_id IS NULL
  AND mc.space_id IS NULL
  AND EXISTS (
      SELECT 1
      FROM facilities_ok fo
      WHERE fo.space_id = s.space_id
  )
GROUP BY
    s.space_id,
    s.space_code,
    s.space_name,
    s.space_type,
    s.capacity,
    s.current_status
ORDER BY
    s.capacity ASC,
    s.space_code ASC;
\end{lstlisting}

The facility summary aggregates every facility of a qualifying space with
\texttt{STRING\_AGG}, so the caller sees exactly what is installed. Executed
with \texttt{@slot\_start = `2024-09-16T10:00:00'}, \texttt{@slot\_end =
'2024-09-16T12:00:00'}, \texttt{@minimum\_capacity = 20} and the two-facility
list \texttt{N'["T14 Projector","T14 Whiteboard"]'}, the query found exactly
one available space (as expected from the multi-facility matching): Computer
Lab 165 (\texttt{T14-IN-0066}, space~205065) with capacity 35, status
\texttt{available}, and the facility summary shown in
Table~\ref{tab:aq-q2}. With the empty facility list the same query returns all
capacities and locations free of booking and maintenance conflicts.

\subsection{Approved Bookings Affected by Escalation (Report~4)}

The last report supports business rule NR4. When the impact level of an
\emph{advisory} maintenance record is escalated to \texttt{out-of-service},
all already-approved bookings that overlap the maintenance period must be
identified so that staff can contact the requesters. The query therefore
operates on maintenance \emph{history} events rather than on the current
impact level of the maintenance record: it filters
\texttt{maintenance\_impact\_history} for rows with
\texttt{prior\_level = `advisory'} and \texttt{new\_level =
`out-of-service'}, joins those events to the affected maintenance record, to
the confirmed bookings overlapping the maintenance interval, and to the
advisory acknowledgement recorded when the booking was submitted:

\begin{lstlisting}[style=sqlreport]
WITH escalation_events AS (
    SELECT
        mih.history_id,
        mih.maintenance_id,
        mih.changed_at AS escalation_time,
        mih.changed_by,
        mih.prior_level,
        mih.new_level,
        mih.reason AS escalation_reason,
        m.space_id,
        m.problem_description,
        m.start_time AS maintenance_start_time,
        m.completion_time AS maintenance_end_time
    FROM dbo.maintenance_impact_history mih
    INNER JOIN dbo.maintenance m
        ON m.maintenance_id = mih.maintenance_id
    WHERE mih.prior_level = 'advisory'
      AND mih.new_level = 'out-of-service'
      AND m.is_deleted = 0
      AND (
          @from_escalation_time IS NULL
          OR mih.changed_at >= @from_escalation_time
      )
      AND (
          @to_escalation_time IS NULL
          OR mih.changed_at < @to_escalation_time
      )
      AND (
          @maintenance_id IS NULL
          OR mih.maintenance_id = @maintenance_id
      )
)
SELECT
    ee.escalation_time,
    escalator.full_name AS escalated_by,
    ee.new_level,
    s.space_id,
    s.space_code,
    s.space_name,
    b.booking_id,
    b.requested_start_time,
    b.requested_end_time,
    b.purpose,
    b.status AS booking_status,
    requester.full_name AS requester_name,
    requester.email AS requester_email,
    baa.acknowledged_at,
    ROUND(overlap_seconds / 3600.0, 2) AS overlap_hours
FROM escalation_events ee
INNER JOIN dbo.booking_approvals ba
    ON ba.decision = 'approved'
   AND ba.decision_time <= ee.escalation_time
INNER JOIN dbo.bookings b
    ON b.booking_id = ba.booking_id
   AND b.space_id = ee.space_id
   AND b.is_deleted = 0
   AND b.status IN ('approved', 'checked_in', 'completed')
   AND b.requested_start_time < COALESCE(
       ee.maintenance_end_time,
       CONVERT(DATETIME2, '9999-12-31T23:59:59')
   )
   AND b.requested_end_time > ee.maintenance_start_time
INNER JOIN dbo.booking_advisory_acknowledgement baa
    ON baa.booking_id = b.booking_id
   AND baa.maintenance_id = ee.maintenance_id
INNER JOIN dbo.spaces s
    ON s.space_id = ee.space_id
INNER JOIN dbo.users requester
    ON requester.user_id = b.requester_id
INNER JOIN dbo.users escalator
    ON escalator.user_id = ee.changed_by
ORDER BY
    ee.escalation_time DESC,
    b.requested_start_time ASC,
    b.booking_id ASC;
\end{lstlisting}

The dependency on the acknowledgement join is deliberate: a booking can be
reported only if the requester was informed of the advisory at submission
time, which is exactly the population that NR4 wants contacted. For each row
the procedure also computes \texttt{overlap\_hours}, the portion of the
booking interval that falls inside the maintenance period, so that staff can
reprioritise the follow-up by impact size. The query is strictly read-only:
it never mutates or cancels bookings (the concurrency-safe cancellation
procedures of Task~12 are the only writers in that domain).
